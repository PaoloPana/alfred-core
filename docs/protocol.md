# Wire protocol (version 4)

This document describes exactly what an Alfred module puts on the MQTT broker, so that modules written in other languages
can talk to the Rust ones. Version 4 is the first MQTT version: ZeroMQ peers (version 3 and older) cannot interoperate.

## MQTT usage

| Item | Value |
|------|-------|
| MQTT version | 5 |
| Topic | the Alfred topic with `.` replaced by `/`: `event.telegram.new_message` → `event/telegram/new_message` |
| Subscription | the Alfred topic `a.b` → the filter `a/b/#` (whole segments, includes `a/b`); the empty topic → `#` |
| Payload | exactly one Alfred message (below) per MQTT PUBLISH |
| QoS | default 1 (configurable). Delivery is at least once: receivers must drop duplicates by `id` |
| Retain | `false` for messages; `true` for presence |
| Content type property | `application/vnd.alfred.message` (informative), payload format indicator `0` (binary) |
| Client id | module name, plus `-<instance id>` if any; `clean_start = false`, session expiry 3600 s by default |

### Presence

`module/<client id>/status` (QoS 1, retained) with the plain UTF-8 payload `online` (published after each connection)
or `offline` (last will, and published on a clean disconnect). These payloads are **not** Alfred messages.

### Module info

A module subscribes to `module/info/request` (`module.info.request`). When it receives a message there it publishes, on
`module/info/response`, a message of type `Text` (`0x01`) whose payload is the module name (UTF-8) and whose `params` are the
module capabilities. `AlfredModule` also publishes the same on start, with type `ModuleInfo` (`0xFF`).

## Message layout

```
+---------+----------------------+------------------+----------------+
| version | header length        | header           | payload        |
| 1 byte  | 4 bytes, big endian  | MessagePack map  | rest of bytes  |
+---------+----------------------+------------------+----------------+
```

- `version`: `0x04`. A message with any other version must be discarded.
- `header length`: number of bytes of the header (unsigned, big endian). If it is larger than the remaining data, the message is invalid.
- `header`: a [MessagePack](https://msgpack.org/) **map with string keys** (named fields, not an array).
- `payload`: the application data, raw bytes (UTF-8 text for the `Text`/`Stream*` types, a file path as text for `Audio` and `Photo`).

### Header fields

| Key | MessagePack type | Meaning | If missing |
|-----|------------------|---------|------------|
| `id` | str | Unique id of the publication (UUID v4 as text). Generated by the sender on **every** publish, also when a received message is forwarded | `""` |
| `message_type` | uint | See below | `0` (Unknown) |
| `is_final` | bool | Last chunk of a stream | `false` |
| `stream_id` | str | Identifies a stream | `""` |
| `sequence` | uint (32 bit) | 0-based position of a chunk in its stream | `0` |
| `params` | map str → str | Free parameters | `{}` |
| `response_topics` | array of str | Topics where to send the responses, in order | `[]` |
| `sender` | str | Free identifier of the original sender | `""` |

Forward compatibility: a decoder **ignores unknown keys** and uses the default of missing ones; new keys can therefore be added
without changing the version, which changes only for incompatible changes. Encoders write the keys in the order of the table
(Rust does), but the order does not matter when decoding.

### Message types

| `message_type` | Name |
|----------------|------|
| `0x00` | Unknown |
| `0x01` | Text |
| `0x02` | Audio |
| `0x03` | Photo |
| `0x81` | StreamText |
| `0x82` | StreamAudio |
| `0x83` | StreamPhoto |
| `0xFF` | ModuleInfo |

An unknown value makes the message invalid (it is discarded, not an error for the receiver).

### Duplicates

A receiver keeps the ids of the last messages it received (the Rust implementation keeps 1024) and drops a message whose `id` is
already in the cache. Messages with an empty `id` are never dropped.

### Example

A `Text` message with `id` `"i"`, payload `hi` and everything else default:

```
04 00 00 00 54                      version 4, header length 84
88                                  map with 8 entries
  a2 "id"            a1 "i"
  ac "message_type"  01
  a8 "is_final"      c2
  a9 "stream_id"     a0
  a8 "sequence"      00
  a6 "params"        80
  af "response_topics" 90
  a6 "sender"        a0
68 69                               payload "hi"
```

(the same bytes are checked by the test `wire_layout_is_version_length_header_payload`.)

## Python

```python
import struct
import msgpack

PROTOCOL_VERSION = 4

def encode(header: dict, payload: bytes) -> bytes:
    header_bytes = msgpack.packb(header, use_bin_type=True)
    return bytes([PROTOCOL_VERSION]) + struct.pack(">I", len(header_bytes)) + header_bytes + payload

def decode(data: bytes):
    if not data or data[0] != PROTOCOL_VERSION:
        raise ValueError("unsupported protocol version")
    (length,) = struct.unpack(">I", data[1:5])
    if len(data) < 5 + length:
        raise ValueError("header length exceeds message length")
    header = msgpack.unpackb(data[5:5 + length], raw=False)
    return header, data[5 + length:]
```

With `paho-mqtt` 2.x use `protocol=mqtt.MQTTv5`, publish with `qos=1` on the `/` topic and set the same client id, `clean_start=False`
and session expiry (`properties.SessionExpiryInterval`) if the module must receive what it missed while offline.
Generate `id` with `str(uuid.uuid4())` and drop repeated ids. This snippet and a Rust module have been checked to exchange
messages in both directions through Mosquitto.
